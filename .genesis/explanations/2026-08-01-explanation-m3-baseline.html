Background

What is remex-ai?

remex-ai is a multi-tenant conversational agent platform that learns about user preferences and context. It needs to remember conversations so it can retrieve relevant facts later—think of a personal AI assistant that remembers what you've told it.

The challenge: when you have millions of past conversations, how do you efficiently find what's relevant to the current question? That's where vector embeddings and semantic search come in.

Vector Embedding: A fixed-length list of numbers representing the semantic meaning of text. For example, "I love Python" and "Python is my favorite language" produce very similar embeddings because they express the same idea. The M3 system uses 384-dimensional embeddings.

The Memory Record: Data Structure

Each stored fact is a MemoryRecord with these core fields:

Field Type Purpose
id UUID Unique identifier
tenant_id UUID Multi-tenant isolation; which customer owns this?
user_id UUID Within a tenant, which user owns this?
content String The human-readable text (e.g., "I prefer Python")
embedding vector(384) Semantic representation; used for similarity search
source_turn_ids UUID[] Which turns created this memory? (provenance)
status Enum "active" or other states; retrieved only if active
RLS (Row-Level Security): Earlier migrations set up PostgreSQL RLS policies that enforce tenant isolation at the database layer. The rule is simple: a query can only see rows where the tenant matches app.current_tenant (a transaction-local variable). Even if a bug leaks a connection, the database itself prevents one tenant from seeing another's data.

The Constraint: Superusers Bypass RLS

By M2, the system was already using Alembic migrations and PostgreSQL RLS. But there was a hidden bug: the application connected as cmis (a superuser), and superusers bypass RLS unconditionally in PostgreSQL. That meant RLS policies were present but not enforced.

M3 solves this by introducing a new non-superuser role cmis_app for application requests. Migrations stay on the owner role (cmiscmis_app—triggering RLS enforcement.

Migration 0003 (Non-Superuser Role): Creates the cmis_app role, grants it minimal permissions on memories tables, and ensures transaction-local tenant GUCs reset after commit (so pooled connections don't leak tenant context).

Intuition

The M3 Workflow

M3 is deliberately naive—a baseline with zero sophistication:

1. Receive Memory
Client sends authenticated POST with text + metadata
→
2. Encode Locally
Text is converted to a 384-dim vector via SentenceTransformers
→
3. Store Everything
Every candidate is persisted; no filtering, no write gate
4. Search Request
Client sends query text + auth headers
→
5. Encode Query
Same encoder; same 384 dimensions
→
6. Vector Similarity
Find nearest neighbors using HNSW index
→
7. Return Results
Top-k memories with similarity scores (0–1 range)

Toy Example

Imagine a single user stores two memories:

Memory ID Content Embedding (simplified)
mem-1 "I love Python" [0.8, 0.2, ...]
mem-2 "Cats are great" [0.1, 0.9, ...]

Later, the user queries "What's my favorite programming language?"

The query embedding is [0.75, 0.25, ...]—semantically very close to mem-1. A cosine-distance search returns mem-1 with a high score (e.g., 0.95), and mem-2 with a low score (e.g., 0.10).

Score Formula: score = 1 - (cosine_distance / 2)
This converts the pgvector distance (0–2 range) to a 0–1 similarity score. Clamped to prevent edge cases: GREATEST(0.0, LEAST(1.0, ...))

Why "Naive"?

M3 stores everything. No filtering. Later phases (M5, M7) will add:

  • M5 Write Gate: A learned classifier decides which facts are worth remembering.
  • M7 Retrieval Ranking: Multiple signals (semantic relevance, recency, importance) are combined to rank results better.

For now, M3 is the oracle baseline: it recalls everything that was stored, so we can measure what headroom M5/M7 have to improve.

Code Implementation

1. Authentication & Multi-Tenancy

File: app/api/deps_auth.py

Every API request must carry two headers: X-Tenant-ID and X-User-ID. This is a host-app boundary—we trust the frontend to pass the right identity.

@dataclass(frozen=True)
class AuthContext:
    tenant_id: UUID
    user_id: UUID

def authenticated_identity(
    tenant_id: Annotated[UUID, Header(alias="X-Tenant-ID")],
    user_id: Annotated[UUID, Header(alias="X-User-ID")],
) -> AuthContext:
    return AuthContext(tenant_id=tenant_id, user_id=user_id)

FastAPI's Depends() extracts these headers on every request and creates an AuthContext. If either header is missing or invalid, the request fails with HTTP 422.

2. Encoding: SentenceTransformers

File: app/embedding/local_encoder.py

The encoder is a lazy singleton. On first call, it loads the pre-baked model from the Docker image and validates that it emits exactly 384 dimensions:

@lru_cache(maxsize=1)
def get_encoder() -> LocalEncoder:
    return LocalEncoder()

class LocalEncoder:
    def __init__(self, model_path: str | None = None) -> None:
        path = model_path or os.environ.get(
            "EMBEDDING_MODEL_PATH", DEFAULT_MODEL_PATH
        )
        model_class = getattr(
            import_module("sentence_transformers"), "SentenceTransformer"
        )
        self._model = cast(
            _SentenceTransformerModel,
            model_class(path, local_files_only=True, device="cpu"),
        )
        dimension = self._model.get_embedding_dimension()
        if dimension != EMBEDDING_DIMENSION:
            raise RuntimeError(
                f"encoder emits {dimension} dimensions; schema requires {EMBEDDING_DIMENSION}"
            )
Key Detail: local_files_only=True means the model is offline. The Docker image pre-downloads it; no network calls during inference.

3. Vector Storage & Retrieval

File: app/retrieval/vector.py

Storage inserts a memory row with the embedding as a pgvector:

def store_memory(
    *,
    tenant_id: UUID,
    user_id: UUID,
    memory_type: MemoryType,
    content: str,
    source_turn_ids: list[UUID],
    embedding: list[float],
    importance: float = 0.5,
) -> MemoryRecord:
    with (
        get_tenant_connection(str(tenant_id)) as conn,
        conn.cursor(row_factory=dict_row) as cur,
    ):
        row = cur.execute(
            """
            INSERT INTO memories (
                tenant_id, user_id, type, content, embedding,
                source_turn_ids, importance
            )
            VALUES (%s, %s, %s, %s, %s::vector, %s, %s)
            RETURNING ...
            """,
            (tenant_id, user_id, memory_type.value, content,
             _vector_literal(embedding), source_turn_ids, importance),
        ).fetchone()
    return MemoryRecord.from_row(row)
Tenant Connection: get_tenant_connection(str(tenant_id)) connects as cmis_app and sets the transaction-local GUC: app.current_tenant = tenant_id. The RLS policy sees this and allows only matching rows.

Retrieval searches for neighbors using pgvector's cosine-distance operator (<=>) and an HNSW index:

def retrieve_similar(
    *,
    tenant_id: UUID,
    user_id: UUID,
    query_embedding: list[float],
    limit: int,
) -> list[VectorHit]:
    vector = _vector_literal(query_embedding)
    with (
        get_tenant_connection(str(tenant_id)) as conn,
        conn.cursor(row_factory=dict_row) as cur,
    ):
        rows = cur.execute(
            """
            SELECT id, tenant_id, user_id, type, content, source_turn_ids,
                   created_at, updated_at, importance, decay_weight, status,
                   NULL::vector AS embedding, supersedes, write_gate_decision,
                   GREATEST(0.0, LEAST(1.0, 1.0 - (embedding <=> %s::vector)))
                       AS score
            FROM memories
            WHERE user_id = %s
              AND status = 'active'
              AND embedding IS NOT NULL
            ORDER BY embedding <=> %s::vector
            LIMIT %s
            """,
            (vector, user_id, vector, limit),
        ).fetchall()
    return [VectorHit(memory=MemoryRecord.from_row(row), score=float(row["score"]))
            for row in rows]
User Scope: The WHERE clause filters by user_id = %s not just tenant. This is deliberate: a tenant's multiple users don't share memories. RLS enforces tenant isolation; this app-level filter adds per-user scoping.

4. API Routes

File: app/api/routes_memories.py (write) and app/api/routes_retrieve.py (read)

Create memory (POST /v1/memories):

@router.post("/memories", response_model=MemoryResponse,
             status_code=status.HTTP_201_CREATED)
def create_memory(
    request: CreateMemoryRequest,
    identity: Annotated[AuthContext, Depends(authenticated_identity)],
    encoder: Annotated[Encoder, Depends(get_encoder)],
) -> MemoryResponse:
    """M3 baseline only: directly persist every authenticated candidate."""
    record = store_memory(
        tenant_id=identity.tenant_id,
        user_id=identity.user_id,
        memory_type=request.type,
        content=request.content,
        source_turn_ids=request.source_turn_ids,
        importance=request.importance,
        embedding=encoder.encode(request.content),
    )
    return MemoryResponse(...)

Retrieve memories (GET /v1/memories:retrieve):

@router.get("/memories:retrieve", response_model=RetrieveResponse)
def retrieve_memories(
    query: Annotated[str, Query(min_length=1, max_length=10_000)],
    identity: Annotated[AuthContext, Depends(authenticated_identity)],
    encoder: Annotated[Encoder, Depends(get_encoder)],
    limit: Annotated[int, Query(ge=1, le=50)] = 5,
) -> RetrieveResponse:
    hits = retrieve_similar(
        tenant_id=identity.tenant_id,
        user_id=identity.user_id,
        query_embedding=encoder.encode(query),
        limit=limit,
    )
    return RetrieveResponse(
        memories=[
            RetrievedMemory(
                id=hit.memory.id,
                type=hit.memory.type,
                content=hit.memory.content,
                source_turn_ids=hit.memory.source_turn_ids,
                created_at=hit.memory.created_at,
                score=hit.score,
            )
            for hit in hits
        ]
    )

5. Baseline Evaluation

File: evals/run.py, evals/suites/baseline.json

The labeled eval suite has 8 candidate facts (4 "admit", 4 "distractor") and 5 queries (4 with answers, 1 no-answer). For each query, the eval reports:

  • Precision: Of all facts stored, how many should have been? (directly measures admission quality)
  • Recall: Of facts that should have been stored, how many were? (1.0 in M3: we store everything)
  • Precision@k: Of the k=2 results returned by the retriever, how many are relevant? (retrieval ranking quality)

M3 scores: precision=0.500, recall=1.000, precision@2=0.400. This leaves headroom: M5 can improve admission precision to 1.0 (store only relevant facts), and M7 can improve ranking precision@k above 0.4.
