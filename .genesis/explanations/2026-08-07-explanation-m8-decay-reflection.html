M8: Decay + Reflection Background Jobs

Unused memories lose ranking weight on an absolute age schedule and may archive; related memories consolidate into derived summaries — both jobs run off the request path, and retrieve never waits on their row locks.

Background

Beginner mental model

Think of Remex as a selective filing cabinet for an AI assistant. The Write Gate decides what to file and stamps an importance score. Ranking later multiplies that score by a separate decay weight that shrinks when a memory sits unused. M8 is the overnight janitor: it lowers that decay weight on a schedule, archives memories that fall too far, and sometimes writes a short summary that ties related files together — without making the front desk (the retrieve API) wait.

decay_weight vs importance importance is the admission-time judgment (how worth storing this was). decay_weight is an activity dial that starts at 1.0. Effective ranking pressure is roughly importance × decay_weight. Decay never rewrites the Write Gate’s original decision.

What already existed before M8

Schema from M2 already had decay_weight, status (including archived), and audit event enums for decay, archive, and reflect. M5/M6 wired audit recording. M7 hybrid retrieval already ranked with importance and recency. What was missing: anything that moved decay_weight, anything that recorded “this memory was retrieved,” and any reflection summary producer.

System boundaries

API retrieve Packs memories, then best-effort touch_last_accessed. Failures do not flip degraded.
Decay job Scans active tenants; sets absolute decay_weight; may archive; writes audit rows.
Reflection agent Clusters by shared entities; inserts summary + link; fingerprint uniqueness for idempotency.
Read connection Tenant GUC + 150ms statement budget + 50ms lock wait budget.
Invariant: background_jobs_never_block_the_request_path Decay and reflection run only in the worker process. Retrieve must stay fast even if a decay transaction holds the same memory row. The L4 rejection that shaped the final design: an unbounded write-connection touch waited ~10s behind a decay lock.

Intuition

Absolute tiers, not compounding

A common mistake is to multiply weight each night (weight *= 0.9). That compounds: re-running the job, or running it twice by accident, drives memories toward zero and accidental archive. M8 instead maps days unused to a fixed target:

Default decay schedule (env-overridable)
Days since last_accessed_at Target decay_weight Archived?
< 30 1.00 No
30 – 59 0.70 No
60 – 89 0.40 No
≥ 90 0.10 Yes (0.10 ≤ 0.15 threshold)
Toy: importance 0.8, unused 45 days Target weight = 0.70. Ranking contribution ≈ 0.8 × 0.70 = 0.56. Run the job again tomorrow at 46 days unused: still 0.70 — second pass is a no-op (idempotent). Content, write_gate_decision, and importance are untouched.

Before (hypothetical compounding)

Night 1: 1.0 → 0.9. Night 2: 0.9 → 0.81. Double-schedule accident: another ×0.9. Same calendar age, different weights depending on how often the job ran.

After M8 (absolute)

Age 45 days always maps to 0.70. Re-runs write the same end state. Archive is a pure function of the tier + threshold, not of how many times the scheduler woke up.

Reflection as derived data

If two active memories share an entity link (e.g. both mention “Marcus Chen”), they form an edge. Connected components of size ≥ reflection_min_cluster_size (default 2) become candidates. A summary memory is inserted with write_gate_decision.kind = "reflection", and a memory_reflections row stores source ids plus a SHA-256 fingerprint of the sorted source set.

Caption: entity co-occurrence builds an undirected graph; each large enough component yields at most one summary per fingerprint.

source_fingerprint sha256(sorted(source_ids).join(",")). Unique per (tenant_id, user_id, fingerprint). Re-running reflection with the same source set inserts nothing new; a lost race deletes the orphan summary row.

Retrieve must not wait on decay

Broken path (L4 D1)

Decay holds row lock on memory M. Retrieve finishes packing, then UPDATE last_accessed_at via unbounded write connection. Waited ~10s for decay to commit; response still 200 but latency destroyed.

Fixed path

Touch uses get_read_tenant_connection with lock_timeout=50ms. Lock wait raises; route catches and continues. Caller sees 200, memories packed, degraded: false, stale last_accessed_at.

degraded vs touch failure degraded means a retrieval signal failed (vector/keyword/graph). A failed access touch is bookkeeping only — logged and swallowed. Stale access time is acceptable; a stalled request is not.

Code

Walkthrough follows dependency / runtime order: schema → decay → reflection → scheduler → retrieve touch + timeouts.

1. Schema: last_accessed_at + memory_reflections

Migration 0010_decay_reflection.py backfills last_accessed_at from created_at, adds a decay scan index, and creates the derived-data table with RLS (same tenant GUC pattern as memories).

-- memories: unused-age clock
ALTER TABLE memories
  ADD COLUMN last_accessed_at timestamptz NOT NULL DEFAULT now();

-- derived link; summary FK cascades, source ids are uuid[] (no FK)
CREATE TABLE memory_reflections (
  summary_memory_id uuid NOT NULL
    REFERENCES memories (id) ON DELETE CASCADE,
  source_memory_ids uuid[] NOT NULL
    CHECK (cardinality(source_memory_ids) >= 2),
  source_fingerprint text NOT NULL,
  UNIQUE (tenant_id, user_id, source_fingerprint)
);
M9 deletion gap (observed, not fixed here) Deleting the summary cascades the reflection row. Deleting a source leaves a dangling UUID in source_memory_ids. “Summary derived solely from deleted sources must also go” is not enforced by today’s schema.

2. Decay: pure function of unused age

worker/decay_job.py — target_decay_weight chooses the tier; _apply_decay_row skips when weight already matches and archive is not needed; otherwise updates under a tenant write connection and records decay / archive audits in the same transaction.

def target_decay_weight(days_unused: float) -> float:
    if days_unused < 30.0:
        return 1.0
    if days_unused < 60.0:
        return settings.decay_weight_after_30_days  # 0.70
    if days_unused < 90.0:
        return settings.decay_weight_after_60_days  # 0.40
    return settings.decay_weight_after_90_days      # 0.10

# archive when new_weight <= decay_archive_threshold (0.15)

3. Reflection: clusters without recursive summaries

worker/reflection_agent.py loads active memories whose write_gate_decision.kind is not reflection, so summaries do not feed the next clustering pass. Shared entities become pairwise edges; components below min size are dropped.

-- exclude prior reflections from clustering
WHERE user_id = %s
  AND status = 'active'
  AND COALESCE(write_gate_decision->>'kind', '') <> 'reflection'

-- race-safe insert
INSERT INTO memory_reflections (...)
ON CONFLICT (tenant_id, user_id, source_fingerprint) DO NOTHING
RETURNING ...
-- if no row returned: DELETE the orphan summary memory

4. Scheduler: off RQ, off the API

worker/main.py starts a daemon _maintenance_loop next to the heartbeat and RQ worker. Intervals default to 3600s each. Exceptions are logged per pass; one tenant failure does not stop others.

heartbeat loop
|
maintenance: decay + reflection
|
RQ Worker (Write Gate jobs)

Caption: three concurrent loops in one worker process; decay/reflection never enqueue on the API request path.

5. Retrieve touch + dual timeouts

After packing, routes_retrieve.py calls touch_last_accessed inside an inner try/except. The touch itself lives in app/retrieval/vector.py and uses the read connection.

# app/db/session.py — get_read_tenant_connection
set_config('statement_timeout', '150ms', true)  # whole query budget
set_config('lock_timeout', '50ms', true)        # fail lock waits early

# app/retrieval/vector.py — touch_last_accessed
UPDATE memories SET last_accessed_at = now()
WHERE user_id = %s AND id = ANY(%s) AND status = 'active'

# app/api/routes_retrieve.py
try:
    touch_last_accessed(...)
except Exception:
    logger.exception("last_accessed touch failed; continuing")
# degraded still comes only from result.signals_degraded
Why two timeouts statement_timeout alone still lets a blocked UPDATE burn the full 150ms (or hang forever if set to 0). An independent 50ms lock_timeout fails the wait early so fail-open can continue. Verified: with statement timeout disabled, lock timeout still cancelled a contended touch.
