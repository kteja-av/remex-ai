Background

Beginner mental model

When you ask “What is the dog named Xerophyte?”, a pure semantic search might return a vague memory about “having a pet” because the embeddings are similar. M7 adds two more ways to find memories: keyword search (exact words like “Xerophyte”) and a graph signal (entities like “Marcus Chen” linked across memories). A ranking service combines all three, then applies small recency and importance adjustments.

What M3 left behind

Milestone M3 shipped vector-only retrieval via pgvector HNSW. That works for paraphrase but misses exact names, codenames, and relational queries (“Who does Marcus Chen report to?”). ADR-0005 chose hybrid retrieval: vector + Postgres full-text + a lightweight entity-link table, all local (no external API calls on the read path).

Reciprocal Rank Fusion (RRF) A fusion method that scores each memory by summing weight / (k + rank) across signals, where rank is the memory’s position in that signal’s result list. Memories that appear in multiple signals rise to the top without needing comparable raw scores.

Three signals, one read path

Vector pgvector cosine similarity on embeddings. Catches paraphrase; weak on rare exact tokens.
Keyword websearch_to_tsquery + ts_rank_cd on content_tsv. Strong on names and codenames.
Graph Entity links extracted locally; 1-hop expansion finds co-mentioned memories (e.g. manager + report).
Invariants carried forward from M4 The read path still fails open (HTTP 200, degraded: true on total failure) and makes no external calls. Each signal uses get_read_tenant_connection with a 150ms default statement_timeout.

Relevance dominates importance

After RRF fusion, scores are min-max normalized to relevance ∈ [0, 1]. Final score is relevance^exp × tiebreak, where tiebreak is capped at ±2% around 1.0. An exact-name memory at importance 0.05 still beats 60 filler memories at 0.95 — relevance magnitude always wins unless scores are nearly tied.

Graph query plan fix (D1)

Early M7 used one CTE-heavy SQL statement. With stale planner statistics, Postgres nested-looped the inlined CTE hundreds of thousands of times (66s stalls). The fix splits search_graph into three separate = ANY($array) round trips with deterministic ORDER BY memory_id on anchor limits. Cold queries are now ~20ms regardless of stats freshness.

4. Graph signal — three stable statements

File: app/retrieval/graph_links.py (lines 57–136)

# Step 1: anchor memories matching query entities (LIMIT 20, ORDER BY memory_id)
direct_ids = SELECT DISTINCT memory_id ... entity = ANY(%s) ... LIMIT 20

# Step 2: bridge entities co-occurring on anchor memories (LIMIT 20)
bridge_entities = SELECT DISTINCT entity ... memory_id = ANY(direct_ids) ...

# Step 3: bridged memories via bridge entities (no LIMIT — known fan-out risk at scale)
bridged_ids = SELECT DISTINCT memory_id ... entity = ANY(bridge_entities)
  AND NOT (memory_id = ANY(direct_ids))

# Score: direct=2.0, bridged=1.0; fetch memory rows, sort, return top limit
