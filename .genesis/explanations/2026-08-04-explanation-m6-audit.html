Background

The trust question

When an AI assistant recalls a fact about a user, a natural follow-up is: why do you know this? M2 created the memory_audit table alongside memories, but until M6 nothing wrote to it on the live request path. M5 added a Write Gate that judges candidates and stores a write_gate_decision JSONB trace on admitted rows — but rejected candidates left their trace only in the ephemeral Redis job result (24-hour TTL).

Audit trail: An ordered list of immutable events explaining how a memory came to exist (or why a candidate was rejected). Each row records event, actor, source_turn_ids, optional detail (including write-gate trace), and created_at.

Invariant: append-only audit Application code never UPDATEs or DELETEs audit rows on the request path. Test teardown uses app.bypass_audit_immutability = on on the owner connection with RLS disabled — not available to cmis_app.

Intuition

Two enforcement layers

Append-only is enforced twice, for different threat surfaces:

Layer 1 — REVOKE (request path)

REVOKE UPDATE, DELETE ON memory_audit FROM cmis_app

Every API and worker connection uses cmis_app. Attempts raise permission denied. This is the real control on production traffic.

Layer 2 — BEFORE triggers (defense in depth)

Triggers on UPDATE and DELETE raise memory_audit is append-only unless app.bypass_audit_immutability = on.

Covers owner-role accidents, future grant drift, and migration tooling — but bypass GUC is settable by any role today (non-blocking follow-up).

Admit vs reject: different shapes

Admit path

memory_id = new row's UUID

event = admit

actor = write_gate or direct_write

detail may include write_gate_trace

Queryable via GET /v1/memories/{id}/audit

Reject path

memory_id = NULL (no memory row exists)

event = reject

detail includes reason + full trace

Not visible via per-memory audit API (no id to query)

Toy example: Write Gate admit

Input: POST /v1/memories:evaluate with content "The user enjoys hiking on weekends."
PII scan: OK
→
Judge: admit
→
store_memory + audit (one txn)
→
Job result: memory_id

Caption: One admit audit row links to the memory. GET /v1/memories/{memory_id}/audit returns one event with judge rationale in detail.write_gate_trace.

Toy example: Write Gate reject

Input: Candidate content judged as assistant noise (not user-specific).
PII scan: OK
→
Judge: reject
→
record_audit_event (reject, memory_id NULL)
→
Return rejected to job

Caption: Reject audit is durable in Postgres but not tied to a memory id — M9 may add tenant-scoped reject listing.

Access control on read

get_audit_trail first verifies the memory exists and belongs to the requesting user_id. Same tenant but different user → 404 (closes in-tenant IDOR found in L4 REJECT). Cross-tenant → RLS returns no rows → 404.

2. record_audit_event — single insert primitive

File: app/audit/log.py (lines 14–51)

def record_audit_event(
    *, tenant_id, event, actor, source_turn_ids,
    memory_id=None, detail=None, conn=None,
) -> AuditEventRecord:
    if conn is None:
        with get_tenant_connection(str(tenant_id)) as owned_conn, ...
            row = _insert_audit_row(cur, ...)
        return AuditEventRecord.from_row(row)

    with conn.cursor(...) as cur:
        row = _insert_audit_row(cur, ...)  # same transaction as caller
    return AuditEventRecord.from_row(row)

The optional conn parameter lets store_memory commit memory + audit atomically.

3. store_memory — admit audit in same transaction

File: app/retrieval/vector.py (lines 28–80)

with get_tenant_connection(str(tenant_id)) as conn, conn.cursor(...) as cur:
    row = cur.execute("INSERT INTO memories ...").fetchone()
    record_audit_event(
        tenant_id=tenant_id,
        event=AuditEvent.ADMIT,
        actor=audit_actor,          # "direct_write" or "write_gate"
        source_turn_ids=source_turn_ids,
        memory_id=row["id"],
        detail=detail,              # write_gate_trace when present
        conn=conn,                  # shared connection
    )
return MemoryRecord.from_row(row)

4. Write Gate — reject before return, admit via store_memory

File: worker/write_gate.py

# PII blocked — no judge call, no memory
record_audit_event(
    tenant_id=..., event=AuditEvent.REJECT,
    actor=trace.actor, source_turn_ids=...,
    detail={"outcome": "rejected", "reason": "pii_blocked",
            "write_gate_trace": trace.to_dict()},
)

# Judge reject — same pattern, reason: "judge_reject"

# Admit — audit inside store_memory
record = store_memory(..., write_gate_decision=trace_dict,
                      audit_actor=trace.actor)

Reject audit uses its own connection (separate transaction from a non-existent memory insert). Worker crash between judge reject and audit commit is a residual gap noted in quiz-me.
