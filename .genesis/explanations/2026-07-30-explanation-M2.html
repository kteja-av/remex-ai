M2 lays the data foundation for the Cognitive Memory Intelligence System (CMIS): typed memories and memory_audit tables, Alembic-owned schema (including the pgvector extension), Python dataclasses that mirror the schema, and PostgreSQL row-level security (RLS) so tenant isolation is enforced by the database — not only by application code. 1. Background

1.1 Mental model: what is CMIS building?

CMIS is a multi-tenant memory service for AI agents. Each tenant (an organization or workspace) stores memory records — facts, episodes, and procedures the agent learned — along with an audit trail explaining why each memory was admitted, updated, or retired. Every durable write must carry provenance (source_turn_ids): which conversation turns produced this memory. Later milestones will add APIs, a write gate, and vector search; M2 only creates the schema and proves the isolation contract.

Definition — Row-Level Security (RLS) A PostgreSQL feature that attaches a policy to a table. Every query — SELECT, INSERT, UPDATE, DELETE — is filtered through that policy. Rows that fail the policy are invisible (reads) or rejected (writes). RLS runs inside the database engine, so even a buggy application cannot accidentally return another tenant's rows if the policy is correct and the connection is not privileged enough to bypass it.

1.2 What M1 left behind

After M1 the stack had Postgres (pgvector image), Redis, a FastAPI api, and a worker — but no tables. The pgvector extension was created at API startup via a FastAPI lifespan hook. That was acceptable bootstrap debt; M2 moves schema ownership to Alembic and removes the lifespan hook entirely.

1.3 Binding decisions

  • ADR-0001 — Postgres + pgvector as the single engine; embeddings are vector(384).
  • ADR-0006 — RLS on every memory-bearing table; FORCE ROW LEVEL SECURITY so the table owner cannot bypass policies.
  • Design doc — per-record fields: id, tenant/user id, type, content, embedding, source turn ids, timestamps, importance/decay weights, status, supersedes link, write-gate decision trace.
  • Threat model §4 — audit log is append-only in intent; every event carries actor, timestamp, and source turn ids.
Invariant introduced tenant_isolation_is_db_enforced — tested by behavioral probes in tests/acceptance/test_m2_rls.py and catalog assertions in tests/invariants/test_rls_enforced.py. A companion invariant (no_durable_write_without_provenance) is partially enforced now via NOT NULL on source_turn_ids; the full invariant test lands in M5.

2. Intuition

2.1 The core idea: one role, one policy, session-scoped tenant

Instead of creating a separate PostgreSQL role per tenant (expensive DDL, hard to operate), CMIS uses one shared application role (cmis_app) and sets a per-connection configuration variable — a GUC (Grand Unified Configuration) — called app.current_tenant before any query runs. Every RLS policy compares tenant_id on the row against that GUC:

tenant_id = nullif(current_setting('app.current_tenant', true), '')::uuid

The policy appears on both USING (reads/updates/deletes) and WITH CHECK (inserts/updates), so a connection claiming tenant A cannot read tenant B's rows or insert a row stamped with tenant B's id.

2.2 Toy example: two tenants, one table

Suppose the database holds three rows after seeding (done by the owner role with RLS temporarily off):

idtenant_idcontent
a1tenant-A"tenant A fact one"
a2tenant-A"tenant A fact two"
b1tenant-B"tenant B secret"

When the application opens a connection for tenant A:

get_tenant_connection("tenant-A")connect as cmis_app via APP_DATABASE_URL
set_config('app.current_tenant', 'tenant-A', false)
SELECT * FROM memoriesRLS policy: tenant_id = 'tenant-A'::uuid
returns rows a1, a2 only
Result: 2 rowstenant B's b1 is invisible

If the GUC is never set (or set to empty string), the policy evaluates to NULL — no row matches — and the query returns zero rows. That is fail-closed: safer than returning everything or throwing errors on every read.

2.3 Why two database roles?

Iter 1's tests failed even though RLS was enabled, forced, and policies existed. Root cause: cmis (the default POSTGRES_USER) is a superuser, and superusers bypass RLS unconditionally — FORCE ROW LEVEL SECURITY only binds the table owner, not superusers.

Before (iter 1)

App connects as cmis (superuser)

RLS policies exist but are ignored

Tenant A sees tenant B's rows

After (iter 2, migration 0003)

App connects as cmis_app (non-superuser)

RLS policies enforced

Cross-tenant reads and forged inserts blocked

Edge case — catalog vs enforcement The invariant test test_rls_enabled_and_forced_on_every_memory_bearing_table checks pg_class and pg_policies — it proves RLS is configured. Only behavioral tests through get_tenant_connection prove RLS is enforced. If someone points APP_DATABASE_URL back at the superuser, catalog tests stay green while isolation tests go red.

2.4 Load-bearing details in the policy

2.5 Known follow-ups (not bugs in M2, but real)

  • Connection pooling (M3) — set_config(..., is_local=false) is session-scoped; a pooled connection can leak the previous tenant's GUC. Fix: SET LOCAL before M3/M4 pool.
  • Audit mutability (M6) — cmis_app has UPDATE+DELETE on memory_audit; a tenant can forge its own audit history until grants are tightened.
  • FK oracle (M9) — FK checks on supersedes bypass RLS; composite (tenant_id, id) FK planned.

3. Code walkthrough

Changes are ordered by dependency: migrations create schema and roles, domain types define contracts, session helpers wire connections, tests prove behavior.

3.1 Alembic bootstrap alembic.ini · migrations/env.py · tests/conftest.py

Alembic is added for schema versioning only — runtime queries still use raw psycopg, not SQLAlchemy ORM. migrations/env.py reads DATABASE_URL (the owner role) and converts it to SQLAlchemy's postgresql+psycopg:// dialect. A session-scoped pytest fixture runs alembic upgrade head before any DB-touching test, so every test starts from a migrated database.

# tests/conftest.py
@pytest.fixture(scope="session", autouse=True)
def migrated_db() -> None:
    command.upgrade(Config("alembic.ini"), "head")

3.2 Migration 0001 — pgvector extension migrations/versions/0001_pgvector_extension.py

Replaces M1's lifespan bootstrap. The extension must exist before the memories.embedding vector(384) column can be created in 0002.

def upgrade() -> None:
    op.execute("CREATE EXTENSION IF NOT EXISTS vector")

The API no longer self-heals schema. An unmigrated database reports pgvector: false in GET /v1/health — migration drift is visible instead of hidden.

3.3 Migration 0002 — tables + RLS migrations/versions/0002_memories_audit_rls.py

Creates memories with all design-doc fields: typed CHECK constraints on type and status, bounded importance/decay_weight, non-null source_turn_ids, optional embedding vector(384), self-referential supersedes, and write_gate_decision jsonb for future write-gate traces.

Creates memory_audit with event CHECK (admit, reject, update, etc.), non-null provenance, and optional detail jsonb.

For each table:

ALTER TABLE memories ENABLE ROW LEVEL SECURITY;
ALTER TABLE memories FORCE ROW LEVEL SECURITY;
CREATE POLICY memories_tenant_isolation ON memories
  USING (tenant_id = nullif(current_setting('app.current_tenant', true), '')::uuid)
  WITH CHECK (tenant_id = nullif(current_setting('app.current_tenant', true), '')::uuid);

3.5 Domain types and dataclasses app/domain/memory.py · app/db/models.py

MemoryType, MemoryStatus, and AuditEvent are StrEnums mirroring the SQL CHECK constraints — the database and Python agree on allowed values. MemoryRecord and AuditEventRecord are frozen dataclasses with __post_init__ validation:

@dataclass(frozen=True)
class MemoryRecord:
    ...
    def __post_init__(self) -> None:
        validate_weight("importance", self.importance)
        validate_weight("decay_weight", self.decay_weight)
        if not self.source_turn_ids:
            raise ValueError("source_turn_ids must be non-empty ...")

from_row() classmethods bridge psycopg dict rows (including JSONB fields that may arrive as strings) into typed Python objects — this is what API handlers will use in later milestones.

3.6 Tenant-scoped connections app/db/session.py · app/config.py · docker-compose.yml

TENANT_GUC = "app.current_tenant"

def get_tenant_connection(tenant_id: str, connect_timeout: int = 2) -> psycopg.Connection:
    conn = psycopg.connect(settings.app_database_url, connect_timeout=connect_timeout)
    conn.execute("SELECT set_config(%s, %s, false)", (TENANT_GUC, tenant_id))
    return conn

Settings now carries two URLs: database_url (owner) and app_database_url (non-superuser). Docker Compose wires both via environment variables with dev defaults.

3.7 API lifespan removed app/api/main.py

M2's main.py is a plain FastAPI app with no lifespan hook — schema is Alembic's job. Comment documents the contract: run alembic upgrade head before serving.

3.8 Tests tests/acceptance/test_m2_rls.py · tests/invariants/test_rls_enforced.py

Acceptance (7 tests) seed two tenants via the owner role, then exercise the request path:

  • tenant A sees only A's memories; tenant B sees only B's
  • empty GUC → zero rows on both tables (fail-closed)
  • audit rows are tenant-scoped
  • cross-tenant INSERT rejected by WITH CHECK
  • MemoryRecord.from_row round-trips defaults
  • source_turn_ids NOT NULL enforced at DB level

The seeded fixture uses fresh UUIDs per test (iter-2 fix for cross-test contamination) and tears down only its own rows in FK order (audit before memories).

Invariants (4 tests) discover memory-bearing tables by name pattern, assert relrowsecurity + relforcerowsecurity + tenant policies covering all verbs, and parametrize a forged-tenant probe across both tables.
