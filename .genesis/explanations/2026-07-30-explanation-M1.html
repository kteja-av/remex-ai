M1 — Compose Skeleton + Health Check

remex-ai · milestone M1 · branch M1 (all files new — this is the first code in the repo) · verified 2026-07-30

This milestone takes the repository from zero source files to a running, four-service Docker Compose stack — Postgres with pgvector, Redis, a FastAPI service, and a separate background worker — with a GET /v1/health endpoint that honestly reports the state of every dependency. Nothing here is a stub: each field in the health payload is computed live against the real dependency, and failures degrade the payload instead of crashing the endpoint.

1. Background

What remex-ai is. This project is a conversational memory system: a service that decides which facts from a conversation are worth remembering, stores them in Postgres with vector embeddings (via the pgvector extension), and retrieves the relevant ones for later turns. The architecture (chosen in the plan's brainstorm as “Approach B”) puts an LLM “judge” that admits or rejects candidate memories in a background worker, so slow LLM calls never sit inside an HTTP request.

Where M1 sits. M1 is deliberately infrastructural. It does not implement memory at all. It proves four things that every later milestone depends on:

  • The whole system runs as one self-hosted Docker Compose stack (ADR-0004) — nothing installed on the host.
  • The database image is pgvector-capable (ADR-0001) and the vector extension actually exists in the database.
  • Redis is in the stack from day one (ADR-0003), because the future Write Gate will be queue-backed.
  • The api and worker are separate processes from the start, making the invariant below structurally true instead of retrofitted in M5.
Invariant guarded by this milestone background_jobs_never_block_the_request_path — background work (eventually LLM judging, decay, reflection) runs in its own service, so a slow or stuck background job can never stall an HTTP response. M1 enforces this two ways: api and worker are separate Compose services, and an invariant test fails the build if any file under app/api/ imports anything from worker/.
Definitions on first use pgvector — a Postgres extension that adds a vector column type and similarity indexes; how the system will store and search embeddings. Docker Compose healthcheck — a command Compose runs periodically inside a container; depends_on: condition: service_healthy makes one service wait for another's check to pass. Heartbeat — a timestamp a process rewrites on a fixed interval; other processes infer liveness from how old it is. Fail-open — returning a successful HTTP response with degraded content instead of an error when a dependency is down.

Prior behavior. There was none — G0 pre-flight confirmed the repo contained zero source files, no Dockerfile, no compose file. So the “before” picture is an empty directory; the “after” picture is this request path:

The api never talks to the worker process directly — it only reads the timestamp the worker left in Redis. Redis is the only meeting point.

2. Intuition

2.1 A smoke detector for the skeleton

The smallest useful mental model: M1 builds the building's frame and installs one smoke detector per system, then wires all the detectors to a single panel (/v1/health). The panel must keep working even when a detector reports trouble — a smoke detector that burns down with the building is useless. That is why the health endpoint never returns 5xx for a dependency failure: each probe catches its own exceptions and reports false, and the endpoint always answers HTTP 200 with "status": "degraded".

2.2 Toy example — reading the payload

Imagine the worker container crashed 40 seconds ago. Postgres and Redis are fine.

ProbeLive resultEffect on payload
_check_postgres()SELECT 1 → row; pg_extension has 'vector'{"reachable": true, "pgvector": true}
_check_redis()PING → PONG{"pong": true}
_check_worker()heartbeat value is 40s old{"heartbeat_age_seconds": 40.0, "fresh": false, "stale_after_seconds": 15}

The aggregate: ok = true && true && true && false → false, so the response is HTTP 200 {"status": "degraded", …}. An operator sees exactly which dependency is sick and how sick (40s old vs a 15s window), not just a red light.

2.3 Why a heartbeat instead of “ping the worker”

The api could try to open a TCP connection to the worker, but the worker has no server socket — it is a loop, not a service you can call. Indirect liveness through a shared store is the standard pattern here: the worker proves it is alive by doing the thing it exists to do (writing to Redis) and the api measures the evidence. This also mirrors the future exactly: in M5 the api will enqueue judge jobs into Redis and the worker will consume them — same channel, same decoupling.

Edge case built into the design Stale threshold (15s) is deliberately 3× the heartbeat interval (5s). The worker can miss two consecutive beats (GC pause, scheduling hiccup, slow Redis) without the health panel declaring it dead. If you raised the interval to 20s without touching the 15s window, the api would permanently report fresh: false — every heartbeat arrives already stale — while docker compose ps still shows the worker healthy, because the Compose healthcheck uses its own hardcoded 30s window (a recorded M1 follow-up).

2.4 Why CREATE EXTENSION lives in app startup (for now)

The pgvector/pgvector:pg16 image ships the extension binaries but does not run CREATE EXTENSION vector in your database — that is a per-database operation. M1 does it in the FastAPI lifespan hook (runs once when uvicorn starts): the simplest place that is guaranteed to execute before the app serves traffic, using the app's own connection string. It is explicitly marked “M1 bootstrap only” — from M2, Alembic migrations own schema. The except psycopg.Error: pass matters: if the database is unreachable at boot, the api still starts, and the health endpoint can then report postgres as down — a startup crash would hide the diagnosis.

3. Code walkthrough

Ordered by execution flow: image → orchestration → worker producer → api consumer → probes → tests.

3.1 One image, two commands — Dockerfile

```1:14:Dockerfile FROM python:3.12-slim ENV PYTHONUNBUFFERED=1 PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=/app WORKDIR /app COPY requirements.txt . RUN pip install --no-cache-dir -r requirements.txt COPY . . CMD ["uvicorn", "app.api.main:app", "--host", "0.0.0.0", "--port", "8000"] ```

Both api and worker services use build: . — one image, different command. PYTHONPATH=/app is what lets python -m worker.main import app.config (the shared settings module). A recorded follow-up notes the two builds produce separately-tagged but identical images today; a shared image: tag should be added before M5.

3.2 Orchestration and the startup contract — docker-compose.yml

```1:65:docker-compose.yml services: postgres: image: pgvector/pgvector:pg16 healthcheck: test: ["CMD-SHELL", "pg_isready -U $${POSTGRES_USER} -d $${POSTGRES_DB}"] redis: image: redis:7-alpine healthcheck: test: ["CMD", "redis-cli", "ping"] api: build: . command: ["uvicorn", "app.api.main:app", "--host", "0.0.0.0", "--port", "8000"] environment: WORKER_HEARTBEAT_STALE_AFTER_SECONDS: ${WORKER_HEARTBEAT_STALE_AFTER_SECONDS:-15} depends_on: postgres: { condition: service_healthy } redis: { condition: service_healthy } healthcheck: test: ["CMD", "python", "-c", "import urllib.request; urllib.request.urlopen('http://localhost:8000/v1/health', timeout=3)"] worker: build: . command: ["python", "-m", "worker.main"] environment: WORKER_HEARTBEAT_INTERVAL_SECONDS: ${WORKER_HEARTBEAT_INTERVAL_SECONDS:-5} depends_on: redis: { condition: service_healthy } healthcheck: test: ["CMD", "python", "-c", "… assert time.time()-float(v.decode()) < 30, 'heartbeat stale'"] ```

Three details carry the design:

  • depends_on: service_healthy — the api does not start until Postgres accepts connections and Redis answers PING. This is what makes docker compose up -d --wait a meaningful demo gate: exit 0 means the whole stack is genuinely ready.
  • The worker's Compose healthcheck re-implements staleness (read key, assert age < 30s) rather than trusting process liveness — a hung loop inside a running container is still caught. Note the hardcoded 30 vs the app's contractual 15s; recorded as a follow-up to read the env var instead.
  • The api's Compose healthcheck calls the real endpoint, so “healthy” at the orchestration layer means “the app boots and serves,” not merely “port open.”

3.3 The producer — worker heartbeat — worker/main.py, worker/heartbeat.py

```9:17:worker/main.py def main() -> None: client = make_client() while True: try: beat(client) except redis.RedisError: time.sleep(1) client = make_client() # reconnect on failure time.sleep(settings.worker_heartbeat_interval_seconds) ``` ```10:15:worker/heartbeat.py def beat(client: redis.Redis) -> None: client.set(HEARTBEAT_KEY, str(time.time())) def make_client() -> redis.Redis: return redis.Redis.from_url(settings.redis_url, socket_timeout=5) ```

The value stored is a plain Unix timestamp string. The reconnect path (except redis.RedisError → rebuild client) means a Redis restart pauses the heartbeat rather than killing the worker; when Redis returns, beats resume and fresh flips back to true on its own. The loop is intentionally a no-op placeholder — M5 replaces the body with a real queue consumer while keeping the process boundary and this test scaffold.

3.4 The consumer — three independent probes — app/api/routes_health.py

```16:54:app/api/routes_health.py def _check_postgres() -> dict[str, Any]: result = {"reachable": False, "pgvector": False} try: with get_connection() as conn: row = conn.execute("SELECT 1").fetchone() result["reachable"] = row is not None and row[0] == 1 ext = conn.execute( "SELECT COUNT(*) FROM pg_extension WHERE extname = 'vector'" ).fetchone() result["pgvector"] = ext is not None and ext[0] > 0 except psycopg.Error: pass return result def _check_worker() -> dict[str, Any]: ... raw = cast(bytes | None, client.get(HEARTBEAT_KEY)) if raw is not None: age = time.time() - float(raw.decode()) result["heartbeat_age_seconds"] = round(age, 3) result["fresh"] = age <= settings.worker_heartbeat_stale_after_seconds ```

Design properties worth noticing:

  • Defaults are pessimistic. Each result dict starts False/None and is only upgraded by positive evidence. An exception mid-probe can never leave a stale true behind.
  • Every probe has a timeout. Postgres connects with connect_timeout=2 (app/db/session.py); Redis clients use socket_timeout=2. A hung dependency delays the health response by seconds, not forever.
  • pgvector is probed independently of reachability — the L4 verifier confirmed that a database without the extension flips only pgvector to false, which is how the iter-1 bug (image present, extension never created) was caught in the first place.
  • The api duplicates the key name and threshold (HEARTBEAT_KEY is defined in three places) rather than importing worker.heartbeat — deliberate: importing the worker's module would break the very invariant the separation test guards. The follow-up is to centralize the constant in app/config.py, which both sides already import.

3.5 Aggregation — the fail-open contract — app/api/routes_health.py

```57:70:app/api/routes_health.py @router.get("/v1/health") def health() -> dict[str, Any]: dependencies = { "postgres": _check_postgres(), "redis": _check_redis(), "worker": _check_worker(), } ok = ( dependencies["postgres"]["reachable"] and dependencies["postgres"]["pgvector"] and dependencies["redis"]["pong"] and dependencies["worker"]["fresh"] ) return {"status": "ok" if ok else "degraded", "dependencies": dependencies} ```

No exception escapes a probe, so this handler cannot 500 on a dependency failure — verified by the L4 checker, which made dependencies unreachable and observed HTTP 200 degraded every time. And the pgvector bootstrap that makes the happy path green:

```11:19:app/api/main.py @asynccontextmanager async def lifespan(app: FastAPI) -> AsyncIterator[None]: try: with get_connection() as conn: conn.execute("CREATE EXTENSION IF NOT EXISTS vector") conn.commit() except psycopg.Error: pass yield ```

3.6 The proof — acceptance and invariant tests

Acceptance (tests/acceptance/test_m1_health.py, 6 tests) runs inside the stack (docker compose run --rm api pytest) and asserts every field of the payload against the live services. The most interesting one proves the heartbeat is a live signal, not a constant:

```43:48:tests/acceptance/test_m1_health.py def test_worker_heartbeat_key_advances() -> None: client = redis.Redis.from_url(REDIS_URL, socket_timeout=2) first = float(client.get(HEARTBEAT_KEY).decode()) time.sleep(6) # > one 5s beat interval second = float(client.get(HEARTBEAT_KEY).decode()) assert second > first, "worker heartbeat is not advancing" ```

Invariants (tests/invariants/test_api_worker_separation.py, 2 tests) guard architecture rather than behavior. The first parses every app/api/**.py file with the ast module and fails on any import of worker.* — this is the machine-enforced form of background_jobs_never_block_the_request_path, and M5 will extend this same test rather than invent a new one. The second asserts the compose file wires app.api.main:app and worker.main as separate commands; it now matches command tokens after iter-1's bug where a string assertion missed the list-form command.
