Background

From store-everything to selective admission

M3 shipped a naive write path: POST /v1/memories embeds and persists every authenticated candidate with no filtering. That baseline is useful for measuring retrieval quality, but it lets assistant noise, third-party content, and low-value facts pollute the store.

M5 introduces the Write Gate — an async admission pipeline that decides whether a candidate fact deserves durable storage. The project chose Approach B (selective admission with a queue-backed write gate) because it keeps retrieval precision as the store grows and produces a replayable decision trace for trust requirements.

Write Gate: A background judge that evaluates each candidate memory and returns admit or reject. Only admitted rows reach Postgres. The host application polls job status rather than blocking on judge latency.

Asymmetric reliability: fail-closed write, fail-open read

M4 hardened the read path to fail open (HTTP 200 with degraded: true). M5 hardens the write path differently:

Path Philosophy Milestone
Read (GET /v1/memories:retrieve) Fail-open — memory is optional context; never 5xx M4
Write (POST /v1/memories:evaluate) Fail-closed on PII — blocked text never leaves the perimeter; queue full → 429 M5
Baseline write (POST /v1/memories) Still available for evals; encoder failure fails loudly M3 (unchanged)

System boundaries after M5

API service Enqueues jobs, returns 202 immediately, polls tenant-scoped job status. Imports only worker.queue.
Worker service Runs RQ consumer; executes PII scan → judge → optional store_memory.
Redis + RQ Job queue with depth cap; sync-test mode uses daemon threads + Redis keys.
Postgres Admitted rows carry write_gate_decision JSONB (schema from M2).
Invariant: background_jobs_never_block_the_request_path The evaluate endpoint never waits for the judge. A 30-second artificial judge delay in tests does not slow GET /v1/memories:retrieve — the worker owns the slow work.

Queue back-pressure

When Redis queue depth reaches write_gate_max_queue_depth, new evaluate requests get HTTP 429 — not a hang, not a silent drop. The API checks depth synchronously but does not run the judge.

Decoupling proof: Tests set set_judge_delay(30.0) on the worker, enqueue an evaluate job, then call retrieve. Retrieve completes in under one second because it never waits on the sleeping worker thread.

Code

1. Evaluate endpoint — enqueue and return

File: app/api/routes_memories.py (lines 84–108)

The route builds a serializable payload, checks queue capacity, and returns immediately:

@router.post("/memories:evaluate", status_code=status.HTTP_202_ACCEPTED)
def evaluate_memory(request, identity) -> EvaluateJobResponse:
    if not queue_has_capacity():
        raise HTTPException(status_code=429, detail="write gate queue is at capacity")
    payload = payload_from_request(
        tenant_id=identity.tenant_id,
        user_id=identity.user_id,
        memory_type=request.type,
        content=request.content,
        source_turn_ids=request.source_turn_ids,
        importance=request.importance,
    )
    job_id = enqueue_evaluate(payload)
    return EvaluateJobResponse(job_id=job_id)

The M3 direct-write route remains for baseline evals. Production callers should prefer :evaluate.

2. Queue helpers — the only worker import in API

File: worker/queue.py

Production mode enqueues to RQ with tenant metadata on the job:

job = queue.enqueue("worker.write_gate.evaluate_candidate", payload, ...)
job.meta["tenant_id"] = tenant_id
job.save_meta()

Tests use WRITE_GATE_SYNC=true: a daemon thread runs evaluate_candidate while status is tracked in Redis at key cmis:sync_job:{tenant_id}:{job_id}.

3. Tenant-scoped job status (L4 fix D2)

File: worker/queue.py — get_job_status

Early M5 returned any tenant's job trace if you knew the job_id. The fix validates ownership before returning results:

def get_job_status(job_id: str, tenant_id: str) -> dict | None:
    # sync-test path: key includes tenant_id
    raw = get_redis_connection().get(_sync_job_key(tenant_id, job_id))
    ...
    job = Job.fetch(job_id, connection=...)
    if str(job.meta.get("tenant_id", "")) != tenant_id:

read_job_status also sets Cache-Control: no-store so shared caches cannot leak traces between tenants.

4. Write Gate processor — PII before judge

File: worker/write_gate.py

def evaluate_candidate(payload: dict[str, Any]) -> dict[str, Any]:
    candidate = _parse_candidate(payload)
    pii = scan_text(candidate.content)
    if pii.status is PiiStatus.BLOCKED:
        trace = WriteGateTrace.blocked_by_pii(candidate=candidate, pii=pii)
        return {"outcome": "rejected", "reason": "pii_blocked", "trace": trace.to_dict()}

    judge = judge_with_fallback(candidate.content)
    trace = WriteGateTrace.from_judge(candidate=candidate, pii=pii, judge=judge)

    if judge.verdict is not AdmissionVerdict.ADMIT:
        return {"outcome": "rejected", "reason": "judge_reject", "trace": trace.to_dict()}

    record = store_memory(..., write_gate_decision=trace.to_dict())
    return {"outcome": "admitted", "memory_id": str(record.id), "trace": trace.to_dict()}
Trace contract: Every outcome — admit, judge-reject, or PII-block — returns a WriteGateTrace with source_turn_ids, pii_verdict, and optional judge_verdict. Admitted traces are also frozen on the memory row.

5. PII pre-send gate

File: worker/pii_filter.py

Regex patterns match email, phone, SSN, and credit-card-like sequences. A match sets PiiStatus.BLOCKED with the pattern labels — no network, no provider call.

6. Judge provider chain

File: worker/llm_providers.py

Configured remote providers (NIM, Gemini) are tried in order with explicit HTTP timeouts. Any failure falls through to LocalRuleJudge — deterministic heuristics used in CI:

  • Starts with "the user" → admit
  • Contains "assistant" → reject
  • Contains "article" or "discussed software" → reject

7. Eval improvement

File: evals/suites/write_gate.json

Same labeled dataset as M3 baseline, but candidates go through evaluate_candidate instead of direct store. Metrics: precision 1.000, recall 1.000, precision@2 0.400 — precision +0.500 vs baseline while recall holds.
