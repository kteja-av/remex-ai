## Quiz-me · Q+A · 2026-08-07

**Q1 (design).** Decay lowers `decay_weight` to absolute 30/60/90-day targets rather than
multiplying `importance` down each pass, and the retrieve touch uses a separate
`lock_timeout` in addition to `statement_timeout`. Why those two choices over the
obvious alternatives (compounding decay of importance; statement timeout alone)?

**A1:** Absolute `decay_weight` targets make the job a pure function of unused age:
re-running at the same age writes the same end state and cannot compound a memory into
accidental archival. Admission-time `importance` stays the Write Gate signal; ranking
uses `importance × decay_weight`, so inactivity deprioritizes without rewriting the
admission judgment. `statement_timeout` alone would still let a blocked touch burn the
full 150ms budget waiting on a decay row lock; an independent `lock_timeout` (50ms)
fails the wait early so the existing fail-open `try/except` around the touch can
continue and return memories. Separating the knobs also keeps the lock budget tight
even if statement timeout is set to 0.

**Q2 (edge case).** Retrieve has already packed memories when `touch_last_accessed`
blocks on a decay-held row lock. What does the caller see (status, `degraded`,
`last_accessed_at`), and which success criterion would break if the touch used the
unbounded write connection again?

**A2:** With the bounded read connection the lock wait raises (`LockNotAvailable` /
query cancel), the touch exception is swallowed, and the response is still **HTTP 200**
with the packed memories and **`degraded: false`** (degraded tracks retrieval-signal
failure, not best-effort access bookkeeping). `last_accessed_at` is left unchanged for
that request — a stale timestamp is acceptable; a stalled request is not. If the touch
used unbounded `get_tenant_connection` again, the request would wait for the decay
transaction (measured previously at ~10s), returning 200 only after the lock released —
breaking "request-path latency is unaffected while both jobs run" and the
`background_jobs_never_block_the_request_path` invariant in practice.

**Q3 (change impact).** M9 must hard-delete a memory and any summary derived solely from
it, while the deletion audit survives. Trace today's `memory_reflections` schema: what
happens if (a) the *summary* row is deleted, (b) a *source* row is deleted, (c) both
sources of a two-source summary are deleted one by one?

**A3:** (a) `summary_memory_id REFERENCES memories(id) ON DELETE CASCADE` removes the
`memory_reflections` link with the summary — derived metadata does not orphan. (b) There
is **no FK** on `source_memory_ids uuid[]`, so deleting one source leaves a dangling id
in the array; the summary memory and reflection row both survive. (c) After both sources
are gone the summary can still exist as an active memory whose only provenance is the
reflection content + dangling source ids — M9's "summary derived solely from deleted
sources must also go" is **not enforced by schema today**. M9 needs an explicit cleanup
(query reflections whose sources are all gone / deleted, delete those summaries) or
normalize sources into an FK table with `ON DELETE` semantics; deletion audit stays on
`memory_audit` (append-only) regardless.
