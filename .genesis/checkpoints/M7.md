### Blocking defect
- **D1 NOT FIXED (masked, not resolved).** `search_graph` cold (immediately after a write
  burst) vs after an owner-run `ANALYZE memory_entity_links`:

  | entities/memory | n=150 | n=200 | n=400 | after ANALYZE (all n) |
  |---|---|---|---|---|
  | 2 | 82ms | 134ms | **TIMEOUT** | 17ms |
  | 3 | 141ms | **TIMEOUT** | **TIMEOUT** | 17ms |
  | 4 | **TIMEOUT** | **TIMEOUT** | **TIMEOUT** | 18ms |

  Cost is entirely stale-statistics plan selection — the same root cause as D1. The B1
  rewrite cut magnitude (66s → 0.35s at n=200, 1.5s at n=400) but not stats sensitivity.
  `EXPLAIN ANALYZE` at n=400 cold: stale `reltuples` → rows=1 estimates → nested loops that
  re-execute the *inlined* `bridge_entities` 1,140× and rescan the `direct` CTE **592,420×**
  (exec 1,543ms). The `LIMIT 20` inside `bridge_entities` is what prevents Postgres from
  flattening `entity IN (SELECT ...)` into a hash semi-join — the bound meant to make the
  query cheap is what forces per-row re-execution. Anchor lookup also applies
  `entity = ANY(...)` as a Filter, not an Index Cond.
  - Migration 0008 `ANALYZE` runs once at migration time (no effect on later data); its
    autovacuum thresholds only apply when autovacuum next wakes (`naptime` 60s default), and
    write-burst-then-read sits inside that window. 0009 `SET STATISTICS 1000` raises sample
    size, not freshness.
- **Criterion 3 not met.** Latency *is* now bounded (~200ms) — real improvement over the 66s
  stall — but bounded by the 150ms `statement_timeout` killing the graph query. Past ~150
  memories/user the read path runs on two signals, not three.
- **The loss is silent.** `rank_memories` catches `QueryCanceled`; `routes_retrieve` returns
  `degraded: false`. No operator signal.
- **Criterion 1's evidence is invalidated by the same condition.** With `search_graph` stubbed
  to `[]`, hybrid p@k drops 0.500 → 0.400 = exactly vector-only, delta +0.000; sole regressing
  query is "Who does Marcus Chen report to?". 100% of the precision win is graph-derived, so
  criteria 1 and 3 fail together after any write burst.

### Non-blocking (new)
- **N10** `test_hybrid_retrieve_stays_within_latency_budget_after_writes` is not load-bearing:
  its seed content yields exactly 2 entities/memory at n=150 — the most favorable cell above.

  82ms and 21ms on two runs of the same config (4× spread) → CI flakiness tracks autovacuum

- **N11** `scorer.py:158` `signals_failed == signals_attempted` is unreachable dead code:
  `signals_attempted` is always ≥2 while `signals_failed` only increments for graph.
- **N12** `direct` CTE has `LIMIT 20` with no `ORDER BY` → nondeterministic anchor selection,

### Fix directions
- Stop plan-dependence: `WITH direct AS MATERIALIZED (...)`, or split into two round trips
  (fetch anchors → fetch bridge entities → single `= ANY($array)` lookup) so each statement
  has a stable index-driven plan regardless of stats.
- Add `ORDER BY` to the anchor `LIMIT`.
- Make signal loss observable (`degraded`, or a `signals_used` field) so criterion 3 is testable.
- Make the latency test adversarial: parameterize entity density (2/4) and n (150/400); assert
  against `settings.read_path_statement_timeout_ms`, not 0.5s.

### Blocking defect
- **D5 (new): the write-path `ANALYZE memory_entity_links` is a silent no-op that floods the DB log.**
  `memory_entity_links` is owned by `cmis`; the write path connects as `cmis_app`. PG16 requires
  table ownership to ANALYZE, so every write emits
  `WARNING: permission denied to analyze "memory_entity_links", skipping it` and **succeeds**.
  - Proof it does nothing: `last_analyze` unchanged after 60 app writes while `n_mod_since_analyze`
    climbed to 120. Cost ≈ 0 (21.3 vs 22.8 ms/write) precisely *because* it is rejected before doing work.
  - **4555 of 4584** postgres log lines over 15 minutes (99.4%) are this warning. The DB log is the
    artifact you need during an incident, and it is now unusable. M10 is the observability milestone;
    this actively regresses observability today.
  - **Landmine.** The obvious remediation on seeing the warning is to grant the privilege — which
    converts this into a *full-table ANALYZE on every memory insert*. Tolerable at 15k rows, an
    outage at millions. The code is one `GRANT` away from a severe write-path regression.
  - **The iter-6 change list credits this line as a D1 fix. It is not.** Every latency number above
    was measured with it doing nothing, so removing it changes no measured behaviour. Fix = delete
    the line; if stats freshness is ever genuinely needed, it belongs in autovacuum tuning (0008)
    or a maintenance job, never in the write transaction.
