## Scope decision · 2026-07-30 (user-approved, before iter 1)

The worker ships in M1 as a **separate compose service running a no-op heartbeat loop** (same image as
`api`, different command), and `GET /v1/health` reports its heartbeat freshness from Redis. Rationale: the
invariant `background_jobs_never_block_the_request_path` becomes structurally true at the first milestone
instead of being retrofitted in M5, and `tests/invariants/test_api_worker_separation.py` starts guarding
`app/api/** → worker/**` imports immediately. M5 extends that test rather than introducing it.
`PLAN.md` M1 and `DONE.html` §3 were updated to match, with the user's approval.

## Quiz-me gate · Q+A

- Q1 (design): the API reads a Redis key it never writes, duplicating the key name + staleness
  threshold instead of importing `worker.heartbeat` to share constants. Why accept the duplication,
  and what would break if you removed it?
- Q2 (edge): if `WORKER_HEARTBEAT_INTERVAL_SECONDS` is raised to 20 with the stale window at 15,
  what does the operator see? What do `docker compose ps` and `GET /v1/health` each report when the
  heartbeat is exactly 20s old, and why do they disagree?
- Q3 (impact): what does `lifespan` in `app/api/main.py` do, why does `postgres.pgvector` report
  `true` partly because of it, and what happens to that field if you delete it today vs after M2
  lands Alembic?
- A1: the invariant `background_jobs_never_block_the_request_path` forbids `app/api/**` importing
  `worker/**`; sharing constants via import would couple the request path to the worker and trip the
  AST invariant test. The duplication is the price of the boundary. Removing it either fails the
  invariant test or weakens it — the structural guarantee M5 depends on. Safe fix (follow-up 3):
  move `HEARTBEAT_KEY` into `app/config.py`, which both sides may import.
- A2: with interval 20s and stale window 15s every heartbeat ages past the window before the next
  beat, so `/v1/health` reports `degraded` permanently despite a healthy worker. At age exactly 20s
  the API says `worker.fresh: false` (20 > 15) while `docker compose ps` says healthy, because the
  compose healthcheck hardcodes 30s (20 < 30) — two independently defined thresholds drifting
  (follow-up 1), the exact drift risk behind Q1.
- A3: `lifespan` runs `CREATE EXTENSION IF NOT EXISTS vector` at API startup, swallowing
  `psycopg.Error` so a DB hiccup never blocks the API from serving. `postgres.pgvector` reads
  `pg_extension`, and reports `true` partly because the lifespan created the extension (the pgvector
  image ships binaries only). Deleting it today: fresh volume → `pgvector: false` → degraded. After
  M2, Alembic owns the schema (extension as first migration), so deleting the lifespan then is safe —
  it is M1 bootstrap code, not schema truth.
