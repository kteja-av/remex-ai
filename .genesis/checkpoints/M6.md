## Quiz-me · Q+A · 2026-08-04

**Q1 (design).** Append-only is enforced twice: `REVOKE UPDATE, DELETE` from `cmis_app`, and `BEFORE` triggers for all roles including owner. Given the request path only connects as `cmis_app`, what threat does the trigger buy, and why is it the weaker layer as written?

**A1:** The **revoke** is the real control on the request path: `cmis_app` cannot UPDATE or DELETE audit rows at all (`permission denied`), which is what the acceptance test observes. The **trigger** is defense-in-depth for everything else: migrations/seeding on the `cmis` owner role, a future accidental `GRANT UPDATE` to `cmis_app`, and TRUNCATE (which bypasses `BEFORE DELETE` triggers but is also revoked). It is the weaker layer because `app.bypass_audit_immutability` is settable by any role without privilege checks — so the trigger does not stop a determined owner or a misconfigured grant; only the revoke blocks `cmis_app` today. The trigger buys **accident prevention on the owner connection** and **belt-and-suspenders if grants drift**; it is not an independent cryptographic guarantee.

**Q2 (edge case).** Write-gate reject calls `record_audit_event` on its own connection (not shared with a memory insert). If the worker is killed between judge `reject` and audit commit, what state is the system in, what does `GET /v1/jobs/{job_id}` show, and which M6 criterion breaks?

**A2:** No memory row exists (reject path never calls `store_memory`). If the worker dies **after** `record_audit_event` commits, the reject audit row is durable and RQ may still mark the job failed (process crash) — `GET /v1/jobs/{job_id}` shows `status: failed` with an error, but the audit row exists (durable reject, awkward job UX). If killed **during** the audit insert before commit, the audit row is absent and RQ reports `failed` — **M6 criterion "every reject produces an audit row" is violated** for that candidate; the ephemeral job trace may also be incomplete. Admit path is safer: memory + admit audit share one transaction in `store_memory`. Mitigation for production: wrap reject audit + job result in one transaction or emit audit before returning to RQ (current code commits audit before return, so crash after commit is the main residual gap).

**Q3 (change impact).** M9 `DELETE /v1/memories/{id}` must hard-delete the memory while the deletion audit row survives. `memory_audit.memory_id` FK references `memories`. What breaks, and how do `ON DELETE SET NULL`, dropping the FK, or soft-delete compare against queryable trails + append-only?

**A3:** A bare `DELETE FROM memories` **fails today** — FK `memory_audit_memory_id_fkey` blocks it while audit rows reference the id. **ON DELETE SET NULL** lets hard-delete succeed; the delete audit row survives with `memory_id = NULL`, but `GET /v1/memories/{id}/audit` returns 404 (memory gone) — trail is orphaned unless M9 adds a tenant-scoped "audit by event id" or includes the deleted id in `detail`. **Dropping the FK** allows delete but loses integrity (audit rows could point at nonexistent ids). **Soft-delete** (`status = 'deleted'`, row retained) keeps `GET /v1/memories/{id}/audit` working, matches retrieval filtering on `status = 'active'`, and append-only holds; a `delete` audit event records the action without removing the memory row — aligns best with "trail queryable per memory id" until a retention purge policy runs. **Recommended for M9:** soft-delete as the user-facing delete + `delete` audit row; defer physical purge to an ops job that uses owner + bypass GUC, or migrate to `ON DELETE SET NULL` with a tombstone id in `detail` if true hard-delete is required.
