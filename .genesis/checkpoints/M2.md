## Quiz-me gate · Q+A

- Q1 (design): the policy reads the tenant from a per-connection GUC
  (`current_setting('app.current_tenant', true)`) instead of per-tenant DB roles or a query
  parameter. What does that buy and cost, and why are the `true` argument and the `nullif(..., '')`
  wrapper load-bearing? What happens if you drop each with the GUC never set?
- Q2 (edge): if someone points `APP_DATABASE_URL` at the `cmis` superuser and everything still
  boots, which tests go red, which stay green, and what does that say about whether
  `test_rls_enforced.py` tests enforcement or configuration? What one test would you add?
- Q3 (impact): in M3 a connection pool arrives; in M6 `GET /v1/memories/{id}/audit` makes the
  trail user-facing. Trace what in today's artifact becomes wrong for each — session-scoped
  `set_config`, and cmis_app's exact grants on `memory_audit`. Which is the worse trust failure?
- A1: one shared role + one policy per table for all tenants — no per-tenant role provisioning or
  DDL churn; the cost is the connection must set the GUC correctly and it is session state (the
  pooling hazard in follow-up 4). `true` (missing_ok) makes an *unset* GUC return NULL → the
  predicate is NULL → zero rows: fail-closed as an empty set instead of an error storm on the
  read path. `nullif(..., '')` folds an explicitly empty GUC into the same NULL path — without it,
  `''::uuid` raises. Drop `true` with GUC unset → every query errors (still closed, but noisy);
  drop `nullif` with GUC set to '' → cast error. Isolation holds either way; ergonomics and
  fail-open-vs-error behavior are what change.
- A2: every behavioral test through `get_tenant_connection` goes red (cross-tenant rows visible,
  forged INSERT succeeds, forged-claim probes see rows) because superusers bypass RLS even with
  FORCE. The catalog assertions (relrowsecurity / relforcerowsecurity / pg_policies) stay green —
  they test *configuration*, not *enforcement*; only the behavioral probes prove enforcement.
  Add: `SELECT rolsuper OR rolbypassrls FROM pg_roles WHERE rolname = current_user` is false on a
  `get_tenant_connection` — a one-line tripwire that fails the moment the request path reconnects
  as a privileged role.
- A3: M3 pooling: `set_config(..., is_local=false)` leaves the tenant GUC on the connection; a
  pooler handing it to another tenant's request leaks that tenant's rows — cross-tenant read via
  connection reuse. M6 audit endpoint: cmis_app holds UPDATE+DELETE on `memory_audit`, so a tenant
  can rewrite or erase its own audit history — the "why do you know this?" trail becomes forgeable
  and repudiation returns. The audit gap is the worse trust failure: the pool leak is severe but
  loud and gets fixed when the pool is introduced (follow-up 4); a forgeable audit trail is silent
  and strikes the system's core accountability promise (threat model: Tampering + Repudiation).
